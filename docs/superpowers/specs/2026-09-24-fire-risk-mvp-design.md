# Техническая спецификация MVP прогнозирования пожарного риска

**Статус:** черновик для согласования  
**Дата:** 24 сентября 2026 года  
**Связанный PRD:** `tasks/prd-fire-risk-mvp.md`

## 1. Назначение

Документ определяет техническую архитектуру автономного MVP: подготовку журналов СМВУ, временную разметку, обучение multi-horizon модели, выдачу прогнозов, линейную карту пикетов, SMS по ролям, фиксацию решений и заявки.

Главный принцип: pipeline признаков не зависит от происхождения `y`. В MVP используется proxy-разметка, а в дальнейшем тот же процесс обучения получает настоящие решения заказчика.

## 2. Границы системы

```text
CSV и справочники
       ↓
Data preparation
       ↓
Normalized events → Episodes → Feature snapshots
                                   ↑
Proxy labels / Real decision labels
       ↓
Training and evaluation
       ↓
Model artifacts
       ↓
Prediction service
       ↓
Application API → Web UI → SMS adapter
                         ↘ Decisions / Requests
```

Исходные данные считаются неизменяемыми. Производные наборы версионируются по конфигурации, временному диапазону и версии кода.

## 3. Предлагаемый стек

Стек является техническим предложением и может быть изменён до плана реализации:

- Python 3.12, Polars или DuckDB, Parquet — обработка данных.
- CatBoost или LightGBM, scikit-learn — baseline и калибровка.
- FastAPI — сервис прогнозирования.
- ASP.NET Core REST API — основной backend.
- PostgreSQL — прикладные данные.
- React, TypeScript, Vite — web-интерфейс.
- ECharts или Recharts — графики.
- Собственный SVG-компонент — линейная карта пикетов.
- Docker Compose — локальный запуск пакета.

## 4. Контракты исходных данных

### 4.1. SensorEventRaw

```text
event_id: string
channel_id: string
registered_at: timestamp
alarm_flag: boolean
raw_value: string
source_year: int
```

### 4.2. ChannelReference

```text
channel_id: string
engineering_system_type: string
sensor_type: string
sensor_name: string
object_id: string
object_level: int
object_name: string
level2_object_id: string
level2_object_name: string
level1_object_id: string
level1_object_name: string
```

Термин `sensor_type` сохраняется для совместимости с источником, но сущность `channel_id` трактуется как канал данных, а не гарантированно физическое устройство.

### 4.3. StateReference

```text
sensor_type: string
state_set_id: string
state_name: string
alarm_flag: boolean
```

До использования строится отчёт покрытия фактических `sensor_type + raw_value`. Противоречивые пары не разрешаются автоматически.

## 5. Нормализация событий

### 5.1. SensorEventNormalized

```text
event_id
channel_id
object_id
registered_at
sensor_type
sensor_name
alarm_flag
value_kind: numeric | known_state | malfunction | unknown
numeric_value: float | null
state_code: string | null
raw_value
picket_raw: string | null
picket_sort_key: float | null
quality_flags: string[]
```

### 5.2. Правила

- Газовые числовые значения интерпретируются как процент объёма метана; 1% — предметный порог тревоги.
- Даты около Unix epoch, заведомо невозможные отрицательные значения и известные коды производителей маркируются как `malfunction`.
- Неизвестный текст не преобразуется в нормальное или тревожное состояние без правила.
- Все преобразования сохраняют `raw_value` и код применённого правила.

### 5.3. Данные 2021 года

2021 год не исключается целиком. Для каждого канала и дня считаются объём, частота, повторяемость, длительность одинакового состояния и доля тревог. Подозрительный интервал получает флаг `burst`, `stuck` или `historical_artifact`.

- Нормальные интервалы участвуют в обучении.
- Технические аномалии могут участвовать в обучении детектора неисправностей.
- Повреждённые интервалы исключаются из пожарного target builder и baseline активности.

## 6. Пикеты

Парсер извлекает исходный текст и сортировочный ключ из распространённых форм:

```text
ПК3
ПК 87
ПК145+3
ПК 86-85
ПК29–231
```

Точное расстояние не утверждается. `picket_sort_key` используется только для относительного порядка. Исходное обозначение показывается пользователю. Каналы без распознанного пикета входят в группу `unlocated`.

## 7. Эпизоды

Эпизод — связанная последовательность событий одного объекта. Начальное правило:

- события относятся к одному `object_id`;
- новый эпизод начинается после 30 минут без релевантных событий;
- окно настраивается по результатам EDA;
- эпизод хранит начало, конец, каналы, типы, пикетный диапазон и качество данных.

### 7.1. IncidentEpisode

```text
episode_id
object_id
started_at
ended_at
severity
channel_ids[]
sensor_types[]
picket_from
picket_to
quality_flags[]
```

Повторные изменения вероятности связываются с тем же `episode_id`. Это обеспечивает дедупликацию SMS и event-level метрики.

## 8. Источники целевой переменной

### 8.1. Единый интерфейс LabelProvider

```text
get_incidents(period, objects) -> IncidentLabel[]
```

### 8.2. IncidentLabel

```text
incident_id
object_id
started_at
ended_at
incident_type
decision: confirmed_fire | smoke_without_fire | false_alarm |
          maintenance | sensor_malfunction | unknown
confirmed_at
source: proxy | synthetic | dispatcher | imported
confidence
```

### 8.3. MVP ProxyLabelProvider

Строит кандидаты из будущих событий: сочетания дыма, тепла, ручного извещателя, УИР-Р, газа, насосов и массовой согласованной сработки. Результат называется пожарным паттерном СМВУ, а не подтверждённым пожаром.

Label builder имеет отдельную конфигурацию. Признаки для момента `t` используют только данные `≤ t`; целевая метка определяется событиями после `t` внутри выбранного горизонта.

### 8.4. Future DecisionLabelProvider

Импортирует настоящий журнал решений в `IncidentLabel`. Замена провайдера не меняет нормализацию, признаки, обучение, API прогнозов или UI.

## 9. Feature snapshots

Единица обучения:

```text
object_id × scoring_timestamp
```

Начальный шаг — 15 минут. Признаки строятся для окон 5 минут, 30 минут, 3 часа, 6 часов и 24 часа:

- число событий и тревог;
- уникальные каналы и типы;
- число и длительность malfunction-состояний;
- согласованные сработки одного и разных типов;
- дым + тепло, дым + ручной извещатель, дым + УИР-Р;
- насосы как подтверждающий сигнал;
- газ: максимум, среднее, рост, превышение 1%;
- температура: максимум, среднее, наклон;
- продолжительность активного состояния;
- вариативность и энтропия каналов;
- признаки `stuck`, `burst`, `historical_artifact`;
- активность относительно прошлого baseline объекта;
- час, день недели, месяц;
- число доступных каналов каждого типа;
- доля каналов без свежих данных.

Baseline объекта рассчитывается только по прошлым данным. Текущий день и интервалы с `stuck` не участвуют.

## 10. Таргеты

Для снимка в момент `t`:

```text
y_now = подтверждённый/восстановленный активный эпизод в t
y_6h  = начало эпизода в (t, t + 6h]
y_12h = начало эпизода в (t, t + 12h]
y_24h = начало эпизода в (t, t + 24h]
```

Окна одного эпизода получают общий идентификатор группы, чтобы не попадать в разные выборки.

## 11. Модель

### 11.1. Baseline

- Отдельный детектор `now` для реального пожарного паттерна против технического сбоя.
- Отдельные CatBoost/LightGBM-классификаторы для 6, 12 и 24 часов.
- Веса классов или sampling применяются только на train.
- Вероятности калибруются на validation.
- После калибровки применяется монотонная коррекция накопленных вероятностей.

### 11.2. Объяснение

- SHAP или эквивалентные вклады признаков.
- Пользовательское объяснение формируется только из фактически рассчитанных признаков.
- Примеры: `5 дымовых каналов за 30 минут`, `рост температуры на 8°C за 3 часа`, `насосы включены`, `активность ×3,4 относительно нормы`.

### 11.3. Артефакт модели

```text
model_version
feature_schema_version
label_provider_version
training_period
validation_period
thresholds
calibration
metrics
```

## 12. Разделение данных и валидация

Предварительная схема после проверки покрытия каналов:

```text
Train:      2019–2020, нормальные интервалы 2021, 2022–2024
Validation: 2025
Test:       2026
```

Запрещён случайный построчный split. Все снимки одного эпизода находятся в одной части данных. Дополнительно проводится проверка переноса на объектах, исключённых из train.

Метрики:

- row-level PR-AUC как диагностическая;
- event-level Precision, Recall, F1;
- ложные предупреждения на объект в сутки;
- медианное время упреждения;
- доля эпизодов, найденных за 6/12/24 часа;
- SMS на эпизод;
- confusion matrix пожарного паттерна и malfunction.

Proxy-метрики не называются качеством обнаружения реальных пожаров.

## 13. Возраст, ТО и демонстрационный контекст

### 13.1. DeviceMetadata

```text
channel_id
estimated_install_date
estimated_age_years
age_source: first_seen | generated_demo | imported
is_synthetic
last_maintenance_at
maintenance_source: demo | imported | unavailable
```

Генерация выполняется детерминированно с фиксированным seed. Возраст показывается числом в согласованном формате. Источник доступен в tooltip или деталях. Возраст и ТО не участвуют в создании proxy-таргета.

Сварочные работы и ремонтный контекст поступают через отдельный mock-адаптер. При появлении реального источника адаптер заменяется без изменения карточки.

## 14. Уровни тревоги

```text
BLACK  — событие сейчас
RED    — риск в течение 6 часов
YELLOW — риск в течение 12 часов
GREEN  — риск в течение 24 часов
```

Пороги конфигурируются отдельно и калибруются после baseline. Если одновременно превышены несколько порогов, выбирается самый срочный уровень. Эскалация создаёт новую версию предупреждения; деэскалация не удаляет историю.

## 15. SMS

### 15.1. Матрица ролей

| Уровень | Техник | Диспетчер района | Диспетчер ОДС | Группа реагирования |
| --- | --- | --- | --- | --- |
| BLACK | Да | Да | Да | Да |
| RED | Да | Да | Да | Нет |
| YELLOW | Нет | Да | Да | Нет |
| GREEN | Нет | Нет | Да | Нет |

### 15.2. Дедупликация

Ключ: `episode_id + alert_level + recipient_id`. Повтор запрещён до истечения cooldown, кроме ручного повторения или критического правила. Эскалация использует новый уровень и рассылается новым и прежним адресатам.

### 15.3. Интерфейс провайдера

```text
send(message, recipient) -> delivery_id, status
get_status(delivery_id) -> queued | delivered | failed
```

MVP использует эмулятор и журнал доставки. Реальный провайдер подключается адаптером.

## 16. Карточка предупреждения

API и UI сохраняют все согласованные блоки:

- заголовок уровня и горизонта;
- адресаты, приоритет, период обновления;
- время, объект, пикет, вероятность, ID;
- сработавшие каналы с типом, значением, возрастом и ТО;
- динамика вероятности;
- контекст, включая demo-работы при наличии;
- факторы и объяснение;
- рекомендации;
- история эскалации/деэскалации;
- статус решений, заявки и SMS.

## 17. Линейная карта пикетов

SVG-схема строится по `object_id` и `picket_sort_key`. Масштаб относительный. Маркеры каналов группируются при пересечении. Цвет и форма показывают тип и состояние, но рядом сохраняется текстовая метка.

Интеракции:

- масштабирование и горизонтальная прокрутка;
- фильтрация по типу канала и состоянию;
- выделение диапазона активного эпизода;
- tooltip канала;
- переход в карточку предупреждения;
- отдельная панель каналов без пикета.

## 20. Ошибки и деградация

- Неизвестный канал сохраняется в quarantine и не обрушает импорт.
- Неизвестное значение получает `value_kind=unknown`.
- Отсутствующий пикет не исключает канал.
- Недоступность ML-сервиса показывает последний успешный прогноз с отметкой времени и статусом `stale`.
- Ошибка SMS фиксируется и доступна для повторной отправки.
- Отсутствие demo-контекста показывает `данные не предоставлены`, сохраняя структуру карточки.

## 22. Наблюдаемость и воспроизводимость

Каждый импорт, расчёт признаков, обучение и инференс получает `run_id`. Логи содержат версию конфигурации, диапазон данных, количество принятых/отклонённых строк и модель. Персональные телефоны в demo заменяются тестовыми получателями.

## 24. Решения, требующие подтверждения

1. Сохраняем два документа: PRD и эту техническую спецификацию.
2. Используем модель `proxy y сейчас → настоящий y позже`, а не одноразовую синтетическую модель.
3. Данные 2021 года очищаем точечно.
4. Пикетная карта является обязательным экраном MVP.
5. Карточки не сокращают содержание предоставленных примеров.
6. SMS реализуется через адаптер-эмулятор с заданной матрицей ролей.
